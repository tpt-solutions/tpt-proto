# tpt-proto Design Document

**Project name:** tpt-proto  
**Document status:** Full-scope design  
**Implementation model:** Clean-room  
**Primary language:** Rust  
**License:** MIT OR Apache-2.0  
**Compatibility target:** Protocol Buffers-compatible system  
**Scope policy:** This document covers the complete system. No major subsystem is deferred.

---

## 1. Summary

`tpt-proto` is a complete, clean-room, pure-Rust implementation of a Protocol Buffers-compatible ecosystem.

It includes:

- a `.proto` language parser
- a semantic analyzer
- a compiler
- a descriptor model
- a Rust code generator
- a binary wire-format runtime
- a reflection runtime
- JSON mapping
- text format support
- well-known types
- schema linting and diffing
- conformance testing
- service and RPC integration
- security-hardened decoding
- deterministic encoding
- build tooling
- documentation and provenance policies

The goal is not only to encode and decode protobuf messages, but to provide a complete, production-grade protobuf toolchain for Rust.

---

## 2. Goals

`tpt-proto` must achieve the following goals.

### 2.1 Full compatibility

`tpt-proto` must be compatible with the publicly documented Protocol Buffers behavior for:

- proto2
- proto3
- editions
- binary wire format
- JSON mapping
- text format
- descriptors
- well-known types
- schema evolution
- unknown fields
- extensions
- oneofs
- maps
- packed and unpacked repeated fields

### 2.2 Pure Rust

The core compiler, runtime, code generator, and tooling must be implemented in Rust.

Production use must not require:

- protoc
- C++ dependencies
- external binaries
- network access during build

External tools may be used in CI for conformance validation, but not as a required runtime dependency.

### 2.3 Clean-room provenance

`tpt-proto` must be developed as a clean-room implementation.

Allowed inputs:

- public protobuf documentation
- public wire-format documentation
- public language guides
- public conformance behavior
- original design notes
- original tests

Disallowed inputs:

- upstream protobuf implementation code
- existing protobuf crate internals
- copied generated code templates
- proprietary implementations
- AI prompts containing upstream source code

### 2.4 Rust-native developer experience

Generated and runtime APIs must feel natural in Rust.

The project should provide:

- idiomatic structs
- enums
- builders
- rich error types
- optional zero-copy decoding
- clear module organization
- safe defaults
- strong documentation

### 2.5 Production safety

`tpt-proto` must be safe for untrusted input.

It must provide:

- decoder limits
- recursion limits
- allocation limits
- UTF-8 validation
- integer overflow protection
- fuzz-tested parsers and decoders

## 7. Binary wire format

`tpt-proto-core` must implement the complete binary wire format.

### 7.1 Wire types

The following wire types must be supported:

| Wire type | Meaning |
|---:|---|
| 0 | Varint |
| 1 | 64-bit |
| 2 | Length-delimited |
| 3 | Group start |
| 4 | Group end |
| 5 | 32-bit |

Groups are deprecated but required for full compatibility.

### 7.2 Field encoding

Each field must be encoded using:

```text
tag = (field_number << 3) | wire_type
```

followed by the appropriate payload.

### 7.3 Scalar types

The following scalar types must be supported:

```text
int32
int64
uint32
uint64
sint32
sint64
fixed32
fixed64
sfixed32
sfixed64
bool
string
bytes
```

### 7.4 Repeated fields

Repeated fields must support:

- unpacked encoding
- packed encoding
- mixed encoding on input
- deterministic packed output where applicable

Decoders must accept both packed and unpacked forms where required by compatibility rules.

### 7.5 Map fields

Maps must be encoded as repeated synthetic map-entry messages.

Map entries must have:

```text
key = field 1
value = field 2
```

Requirements:

- duplicate map entries must be accepted
- later values should override earlier values by default
- deterministic encoding must sort map entries consistently
- key and value types must be validated

### 7.6 Oneofs

Oneofs must support:

- mutually exclusive fields
- last value wins when multiple oneof fields appear
- correct presence semantics
- idiomatic Rust enum generation

### 7.7 Unknown fields

Unknown fields must be supported.

Default policy:

```text
preserve unknown fields
```

Alternative policies:

```text
discard
fail
```

Preserved unknown fields must be re-encodable.

### 7.8 Extensions

Proto2-style extensions must be supported.

This includes:

- extension ranges
- extension declarations
- extension registries
- dynamic extension lookup
- encoding and decoding extension fields
- option extensions

### 7.9 Groups

Legacy groups must be supported for compatibility.

This includes:

- group start and group end wire types
- matching field numbers
- legacy code generation
- warnings for new usage

### 7.10 Deterministic encoding

`tpt-proto` must provide deterministic encoding.

Deterministic mode must define:

- field order
- map order
- unknown field order
- canonical varint representation
- repeated field order where applicable
- oneof serialization behavior

Deterministic encoding is required for hashing, signing, auditing, and reproducible systems.

## 8. Runtime message model

`tpt-proto` must support multiple message representations.

### 8.1 Owned messages

Owned messages own all data.

Example concept:

```rust
pub struct User {
    pub id: i64,
    pub name: String,
    pub email: Option<String>,
}
```

### 8.2 Borrowed messages

Borrowed messages avoid allocation where possible.

Example concept:

```rust
pub struct UserView<'a> {
    pub id: i64,
    pub name: &'a str,
    pub email: Option<&'a str>,
}
```

### 8.3 Bytes-backed messages

Messages may use efficient byte containers to support shared or sliced buffers.

### 8.4 Dynamic messages

Dynamic messages must be descriptor-driven and require no compile-time generated types.

## 9. Rust code generation

The Rust code generator must produce safe, idiomatic, maintainable code.

### 9.1 Message generation

Generated messages must include:

- struct definition

- default value handling
- presence handling
- unknown field handling
- documentation comments

### 9.2 Enum generation

Generated enums must support:

- named values
- numeric conversion
- unknown values
- open and closed enum semantics
- aliases where applicable

### 9.3 Oneof generation

Oneofs must be represented as Rust enums.

Example concept:

```rust
pub enum Contact {
    Email(String),
    Phone(String),
}
```

### 9.4 Map generation

Maps must use idiomatic Rust map types unless deterministic ordering requires another representation.

### 9.5 Builders

Builders must be generated where enabled.

Builders should validate:

- required fields
- oneof constraints
- invalid enum values
- invalid default values

### 9.6 Presence rules

The code generator must model presence correctly.

Proto3 implicit presence:

```text
missing field equals default value
```

Proto3 explicit optional:

```text
Option<T>
```

Proto2 optional:

```text
Option<T>
```

Proto2 required:

```text
must be present
```

Editions:

```text
presence determined by resolved features
```

## 14. Well-known types

`tpt-proto-wkt` must provide first-class support for all required well-known types.

Special behavior must be implemented for:

### Timestamp

Represents a point in time.

JSON form example:

```json

```

### Duration

Represents a signed length of time.

JSON form example:

```json
"3.5s"
```

### FieldMask

Represents a set of field paths.

JSON form example:

```json
"user.id,user.name"
```

Represents an embedded arbitrary message.

Binary form includes:


JSON form includes:


`Any` requires a type registry.

Represent JSON-like dynamic values.

Represent nullable scalar values.

Supported wrappers:

```text

DoubleValue
FloatValue
Int32Value
Int64Value
```

## 17. Linting and breaking change detection

`tpt-proto-lint` must classify schema changes.

Classification levels:

```text
SAFE
WARNING
BREAKING
```

Examples:

| Change | Classification |
|---|---|
| Add new field | SAFE |
| Add new enum value | SAFE or WARNING depending on enum semantics |
| Remove field and reserve number | SAFE |
| Remove field without reservation | BREAKING |
| Change field number | BREAKING |
| Change field type | BREAKING |
| Rename field but keep number | WARNING |
| Change package | BREAKING |
| Change RPC input type | BREAKING |
| Change RPC output type | BREAKING |

The linter must support machine-readable output.

## 20. Security model

`tpt-proto` must be safe against malicious input.

### 20.1 Decoder limits

The runtime must enforce limits.

Example:

```rust
pub struct DecoderLimits {
    pub max_message_bytes: usize,
    pub max_depth: u32,
    pub max_field_count: usize,
    pub max_unknown_field_bytes: usize,
    pub max_string_bytes: usize,
    pub max_bytes_field_bytes: usize,
    pub max_repeated_entries: usize,
    pub max_map_entries: usize,
}
```

### 20.2 Integer safety

Integer operations must use checked arithmetic where overflow is possible.

### 20.3 UTF-8 validation

String fields must be validated according to schema features and edition rules.

### 20.4 Recursion control

Nested message depth must be bounded.

### 20.5 Allocation control

Allocations must be bounded by limits and sanity checks.

### 20.6 Unsafe policy

Default policy:

```text
no unsafe in core decoding paths
```

Unsafe may only be used when:

- isolated
- documented
- tested
- feature-gated
- justified by measurable benefit

## 28. Risks

### 28.1 Compatibility risk

Protobuf has many edge cases.

Mitigation:

- conformance testing
- extensive fuzzing
- independent compatibility vectors
- conservative defaults

### 28.2 Scope risk

The full system is large.

Mitigation:

- clear component boundaries
- strong testing
- incremental development without removing required scope
- strict prioritization inside workstreams

### 28.3 Adoption risk

Existing crates already have users.

Mitigation:

- pure Rust build
- better diagnostics
- better security defaults
- zero-copy support
- schema tooling
- excellent documentation

### 28.4 Provenance risk

AI-assisted development may accidentally reproduce upstream code.

Mitigation:

- clean-room policy
- no upstream source in prompts
- human review
- provenance logs
- suspicious code rewritten

### 28.5 Trademark risk

The project must not appear official.

Mitigation:

- clear disclaimer
- avoid confusing names
- avoid official logos
- describe compatibility carefully

# tpt-proto-grpc Design Addendum

**Component name:** tpt-proto-grpc  
**Scope:** Complete gRPC-compatible RPC layer for the tpt-proto ecosystem  
**Transport requirement:** HTTP/2  
**License:** MIT OR Apache-2.0  
**Status:** Full-scope design  
**Dependency policy:** The gRPC layer may use pure-Rust HTTP/2 transport components. It must not require external non-Rust binaries for production use.

---

## 1. Purpose

`tpt-proto-grpc` implements the gRPC protocol layer on top of `tpt-proto` message serialization.

It provides:

- gRPC client support
- gRPC server support
- unary calls
- server streaming
- client streaming
- bidirectional streaming
- metadata handling
- status handling
- deadline handling
- cancellation handling
- compression support
- health checking
- server reflection
- interceptors
- observability
- debugging tools

This component turns `tpt-proto` schemas into a complete RPC system.

---

## 2. Relationship to tpt-proto

`tpt-proto` defines and serializes messages.

`tpt-proto-grpc` transports those messages using the gRPC protocol.

The layers are:

```text
.proto schema
  -> tpt-proto compiler/codegen
    -> generated message types
      -> tpt-proto-grpc service traits
        -> gRPC protocol layer
          -> HTTP/2 transport
```

---

## 3. Protocol requirements

`tpt-proto-grpc` must implement the gRPC protocol behavior required for interoperability.

### 3.1 HTTP method and path

Calls must use HTTP/2 POST requests.

The path must follow:

```text
/package.ServiceName/MethodName
```

Example:

```text
/example.UserService/GetUser
```

### 3.2 Content type

The content type must be:

```text
application/grpc
```

Extended content type variants may be supported where required.

### 3.3 Message framing

Each gRPC message must be framed as:

```text
1 byte compression flag
4 bytes big-endian message length
N bytes serialized protobuf message
```

The implementation must support:

- compressed messages
- uncompressed messages
- maximum message size enforcement
- partial frame protection
- stream reset on malformed frames

### 3.4 Metadata

Metadata must be supported as key-value pairs.

Requirements:

- lowercase ASCII metadata keys
- binary metadata values using base64 suffix convention
- request headers
- response headers
- trailers
- metadata size limits
- reserved header protection

### 3.5 Trailers and status

gRPC status must be communicated using trailers.

Required trailer fields:

```text
grpc-status
grpc-message
grpc-status-details-bin
```

The implementation must support:

- normal successful completion
- error completion
- trailer-only responses
- early error responses
- cancellation status
- deadline exceeded status

### 3.6 Timeouts

The `grpc-timeout` header must be supported.

The stack must translate timeouts into:

- request deadlines
- cancellation signals
- remaining-time APIs
- client-side expiry
- server-side expiry

### 3.7 Compression

The stack must support:

- identity encoding
- gzip encoding
- pluggable compression codecs
- `grpc-encoding`
- `grpc-accept-encoding`

Additional compression codecs may be provided if compatible.

---

## 4. Service model

`tpt-proto-grpc` must support all four gRPC method types.

### 4.1 Unary

One request, one response.

```proto
rpc GetUser(GetUserRequest) returns (User);
```

### 4.2 Server streaming

One request, many responses.

```proto
rpc WatchUsers(WatchUsersRequest) returns (stream User);
```

### 4.3 Client streaming

Many requests, one response.

```proto
rpc UploadLogs(stream LogEntry) returns (UploadSummary);
```

### 4.4 Bidirectional streaming

Many requests, many responses.

```proto
rpc Chat(stream ChatMessage) returns (stream ChatMessage);
```

---

## 5. Generated service APIs

The code generator must produce Rust service traits and client stubs.

### 5.1 Server trait example

```rust
#[async_trait]
pub trait UserService {
    async fn get_user(
        &self,
        request: Request<GetUserRequest>,
    ) -> Result<Response<User>, Status>;
}
```

### 5.2 Client stub example

```rust
impl UserServiceClient {
    pub async fn get_user(
        &mut self,
        request: GetUserRequest,
    ) -> Result<Response<User>, Status>;
}
```

### 5.3 Streaming client example

```rust
let mut stream = client.watch_users(request).await?.into_inner();

while let Some(user) = stream.try_next().await? {
    // process user
}
```

### 5.4 Streaming server example

```rust
async fn watch_users(
    &self,
    request: Request<WatchUsersRequest>,
    sink: ServerStreamingSink<User>,
) -> Result<(), Status> {
    // send updates
}
```

The generated API should be strongly typed and async-native.

- extensions map

The API should integrate cleanly with Rust cancellation primitives.
